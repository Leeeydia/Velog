<h2 id="들어가며">들어가며</h2>
<p>ORDA 프로젝트에서 등산로 난이도를 계산하고, 사용자에게 보여주기까지의 전체 흐름을 정리했다.
처음에는 &quot;같은 계산식을 Python이랑 Spring이 둘 다 들고 있으면 비효율 아닌가?&quot; 라는 의문에서 시작했는데, 정리하다 보니 각 레이어가 어떤 역할을 하는지 명확해졌다.</p>
<hr />
<h2 id="전체-구조-3단계로-나눠보기">전체 구조: 3단계로 나눠보기</h2>
<pre><code>Python 파이프라인 (계산)  →  Spring Boot (전달)  →  React 프론트 (표시)</code></pre><p>한 줄로 요약하면 이렇다.</p>
<ul>
<li><strong>Python</strong>이 난이도를 계산해서 DB에 넣고</li>
<li><strong>Spring</strong>이 DB에서 꺼내서 API로 내려주고</li>
<li><strong>React</strong>가 API 응답 받아서 화면에 그린다</li>
</ul>
<p>각 단계를 좀 더 뜯어보자.</p>
<hr />
<h2 id="1단계-python-파이프라인--계산하고-db에-저장">1단계: Python 파이프라인 — 계산하고 DB에 저장</h2>
<p>이 단계는 서비스 배포 전에 한 번 돌리는 오프라인 작업이다.
사용자가 앱을 쓸 때 실행되는 게 아니라, 데이터를 구축할 때 한 번 실행한다.</p>
<p><code>pipeline.py</code>에서 등산로 원천 데이터를 가공하면서 4가지 변수로 난이도 점수를 계산한다.</p>
<pre><code>난이도 점수 = 경사도(0.40) + 고도차(0.25) + 거리(0.15) + 지면상태(0.20)</code></pre><table>
<thead>
<tr>
<th>변수</th>
<th>가중치</th>
<th>설명</th>
</tr>
</thead>
<tbody><tr>
<td>경사도 (slope)</td>
<td>0.40</td>
<td>가장 큰 비중. 경사가 급할수록 어렵다</td>
</tr>
<tr>
<td>고도차 (elevation)</td>
<td>0.25</td>
<td>출발~도착 고도 차이</td>
</tr>
<tr>

<td>0.15</td>
<td>구간 길이</td>
</tr>

<td>0.20</td>
<td>포장/비포장/암석 등</td>
</tr>
</tbody></table>
<p>계산 결과로 나오는 값:</p>
<ul>
<li><code>difficulty_score</code>: 숫자 점수 (예: 28.5)</li>
<li><code>difficulty</code>: 등급 문자열 (easy / moderate / hard / very_hard / extreme)</li>
</ul>
<p>이 두 값을 <code>load_to_postgis.py</code>가 PostGIS DB의 <code>trail_edges</code> 테이블에 저장한다.</p>
<hr />
<h2 id="2단계-spring-boot--db에서-꺼내서-api로-전달">2단계: Spring Boot — DB에서 꺼내서 API로 전달</h2>
<p>Spring Boot가 하는 일은 심플하다.
<strong>DB에 이미 저장된 값을 읽어서 JSON으로 내려주는 것</strong>. 이게 API 구현이다.</p>
<pre><code>프론트에서 요청이 오면
  → DB에서 trail_edges 조회
  → difficulty_score, difficulty 그대로 응답</code></pre><p>Spring은 난이도를 직접 계산하지 않는다.
Python이 이미 계산해서 DB에 넣어뒀으니까, 그걸 꺼내서 전달만 하면 된다.</p>
<p>응답 예시:</p>
<pre><code class="language-json">{
  &quot;difficultyScore&quot;: 28.5,
  &quot;difficulty&quot;: &quot;moderate&quot;
}</code></pre>
<hr />
<h2 id="3단계-react-프론트--api-응답으로-ui-그리기">3단계: React 프론트 — API 응답으로 UI 그리기</h2>
<p>프론트는 Spring API에서 받은 데이터로 사용자에게 보여줄 화면을 그린다.</p>
<p>활용 예시:</p>
<ul>
<li>난이도 색상 배지 표시 (easy=초록, hard=빨강)</li>
<li>별점이나 게이지로 시각화</li>
<li>필터 기능 (&quot;쉬운 코스만 보기&quot;)</li>
<li>코스 비교 시 난이도 점수 활용</li>
</ul>
<p>프론트 입장에서는 <code>difficultyScore</code>랑 <code>difficulty</code> 두 값만 가져다 쓰면 된다.
난이도가 어떻게 계산됐는지는 알 필요 없다.</p>
<hr />
<h2 id="왜-이렇게-나눴을까">왜 이렇게 나눴을까?</h2>
<p><strong>각자 잘하는 일만 하게 하기 위해서다.</strong></p>
<table>
<thead>
<tr>
<th>레이어</th>
<th>역할</th>
<th>핵심</th>
</tr>
</thead>
<tbody><tr>
<td>Python</td>
<td>데이터 계산 + 가공</td>
<td>무거운 연산은 여기서 한 번만</td>
</tr>
<tr>
<td>Spring</td>
<td>API 제공 (DB ↔ 프론트 중간 다리)</td>
<td>계산 없이 전달만</td>
</tr>
<tr>
<td>React</td>
<td>UI 렌더링</td>
<td>받은 데이터 보여주기만</td>
</tr>
</tbody></table>
<p>만약 Spring이 매 API 요청마다 난이도를 직접 계산한다면?
11만 개 넘는 edge 데이터를 요청할 때마다 계산하게 되니까 비효율적이다.
Python이 미리 계산해서 DB에 넣어두면, Spring은 SELECT 한 방이면 끝난다.</p>
<hr />
<h2 id="마무리">마무리</h2>
<p>정리하면 이런 흐름이다:</p>
<pre><code>[Python] 난이도 계산 → DB 저장 (1회성)
[Spring] DB에서 읽기 → JSON 응답 (매 요청)
[React]  API 호출 → 화면 표시 (매 요청)</code></pre><p>&quot;같은 계산식을 두 군데서 들고 있을 필요가 있나?&quot; 라는 의문이 이 구조를 이해하는 출발점이었다.
답은 간단했다 — 계산은 Python이 한 번만 하고, 나머지는 그 결과를 쓰기만 하면 된다.</p>
