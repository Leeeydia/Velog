<p>마이페이지에서 프로필 이미지를 업로드하는 기능을 구현하면서<br />생각보다 많은 오류를 만났다.</p>
<p>프론트에서 작업할 때는 <strong>Supabase 스토리지</strong>로 업로드/URL 저장까지 한 번에 해결했던 경험이 있어서<br />이번에도 “파일만 저장하면 끝이겠지?” 하고 가볍게 생각했다.</p>
<p>그런데 백엔드에서 직접 구현해보니,<br /><strong>DB에 어떤 컬럼을 두고 어떤 이름으로 저장할지(스키마 설계)</strong>부터가 시작이었다.<br />게다가 요청 URL 매핑, MyBatis 쿼리, 파일 저장 경로 설정까지 전부 내가 책임져야 해서<br />작은 불일치 하나만 있어도 바로 에러가 터졌다.</p>
<p>단순히 파일만 저장하면 될 줄 알았지만,<br />URL 매핑 → DB 컬럼 → MyBatis 쿼리 → 파일 경로 설정까지<br />여러 레이어에서 문제가 발생했다.</p>
<hr />
<h2 id="1️⃣-no-static-resource-에러">1️⃣ No static resource 에러</h2>
<h3 id="❌-증상">❌ 증상</h3>
<pre><code>No static resource api/member/me</code></pre><h3 id="🔎-원인">🔎 원인</h3>
<p>Postman에서 다음 URL로 요청을 보내고 있었다.</p>
<pre><code>GET /api/member/me</code></pre><p>하지만 실제 컨트롤러는 아래처럼 정의되어 있었다.</p>
<pre><code class="language-java">@RestController
@RequestMapping(&quot;/api/mypage&quot;)
public class MyPageController {</code></pre>
<p>즉, 존재하지 않는 URL을 호출하고 있었기 때문에<br />Spring이 정적 리소스를 찾다가 예외가 발생한 것이다.</p>
<h3 id="✅-해결">✅ 해결</h3>
<p>올바른 URL로 수정:</p>
<pre><code>GET /api/mypage</code></pre><hr />
<h2 id="2️⃣-file_upload_failed-발생">2️⃣ FILE_UPLOAD_FAILED 발생</h2>
<h3 id="❌-증상-1">❌ 증상</h3>
<pre><code>CustomException: FILE_UPLOAD_FAILED</code></pre><h3 id="🔎-1차-의심">🔎 1차 의심</h3>
<ul>
<li>Postman form-data 설정 오류?</li>
<li>Multipart 설정 문제?</li>
<li>파일 확장자 제한 문제?</li>
</ul>
<p>하지만 모두 정상이었다.</p>
<h3 id="🔎-실제-원인-1--db-컬럼-누락">🔎 실제 원인 1 — DB 컬럼 누락</h3>
<p><code>MEMBER</code> 테이블에 프로필 이미지 컬럼이 없었다.</p>
<pre><code class="language-sql">DESC MEMBER;</code></pre>
<p>확인 결과 <code>profile_image</code> 컬럼이 존재하지 않았다.</p>
<h3 id="✅-해결-1">✅ 해결</h3>
<pre><code class="language-sql">ALTER TABLE MEMBER
ADD COLUMN profile_image VARCHAR(255) NULL;</code></pre>
<hr />
<h2 id="3️⃣-unknown-column-profile_image_url-에러">3️⃣ Unknown column 'profile_image_url' 에러</h2>
<h3 id="❌-증상-2">❌ 증상</h3>
<pre><code>Unknown column 'profile_image_url' in 'field list'</code></pre><h3 id="🔎-원인-1">🔎 원인</h3>
<p>DB에는:</p>
<pre><code>profile_image</code></pre><p>컬럼이 있었는데,</p>
<p>MyBatis 쿼리에서는:</p>
<pre><code class="language-sql">SET profile_image_url = ?</code></pre>
<p>로 업데이트를 시도하고 있었다.</p>
<p>즉, <strong>컬럼 이름 불일치 문제</strong>였다.</p>
<h3 id="✅-해결-방법-선택지">✅ 해결 방법 (선택지)</h3>
<h4 id="방법-a-추천--db-컬럼명을-코드에-맞추기">방법 A (추천) — DB 컬럼명을 코드에 맞추기</h4>
<pre><code class="language-sql">ALTER TABLE MEMBER
CHANGE profile_image profile_image_url VARCHAR(255);</code></pre>
<p>코드에서 이미 <code>profileImageUrl</code>을 사용하고 있었기 때문에<br />DB 컬럼명을 맞춰주는 것이 가장 깔끔했다.</p>
<hr />
<h2 id="4️⃣-파일-저장-경로-문제">4️⃣ 파일 저장 경로 문제</h2>
<h3 id="🔎-기존-설정">🔎 기존 설정</h3>
<pre><code class="language-yaml">file:
  upload:
    profile-dir: uploads/profile</code></pre>
<p>상대 경로 설정이었기 때문에<br />실행 환경에 따라 경로가 꼬일 가능성이 있었다.</p>
<h3 id="✅-개선">✅ 개선</h3>
<pre><code class="language-yaml">file:
  upload:
    profile-dir: ${user.dir}/uploads/profile</code></pre>
<p>프로젝트 루트 기준 절대 경로로 변경하여 안정성을 확보했다.</p>

<h2 id="💡-배운-점">💡 배운 점</h2>
<ol>
<li>파일 업로드는 <strong>DB, 경로, 쿼리, 요청 형식</strong>이 모두 정확히 맞아야 동작한다.</li>
<li>컬럼명은 VO/Mapper/DB가 완전히 일치해야 한다.</li>
<li>상대 경로보다는 <code>${user.dir}</code> 기반 절대 경로가 안전하다.</li>
<li>에러 로그는 절대 무시하면 안 된다.<br />로그가 거의 정답을 말해준다.</li>
