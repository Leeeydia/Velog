<p>현재 ORDA 팀프로젝트에서 나는 C단계를 맡고 있다.<br />C단계의 역할은 B단계에서 정리한 등산로 네트워크 데이터를 받아, 최종 산출물 형태로 가공하는 것이다.</p>
<p>최종적으로 만들어야 하는 산출물은 아래 3개다.</p>
<ul>
<li><code>final_trail_dataset.geojson</code></li>
<li><code>summit_points.geojson</code></li>
<li><code>quality_report.md</code></li>
</ul>
<p>그런데 작업을 시작하면서 한 가지 헷갈렸던 점이 있었다.<br />문서에는 최종 출력 파일 3개만 적혀 있는데, 실제 구현 과정에서는 왜 여러 개의 파이썬 파일을 따로 만들고 있는지 처음에는 감이 잘 오지 않았다.</p>
<p>이번 작업을 하면서 정리한 핵심은 다음과 같다.</p>
<h3 id="최종-산출물과-내부-구현-코드는-다르다">최종 산출물과 내부 구현 코드는 다르다</h3>
<p>문서에 적힌 출력 파일 3개는 말 그대로 <strong>최종 결과물</strong>이다.<br />반면 지금까지 만든 파이썬 파일들은 이 최종 결과물을 만들기 위한 <strong>내부 구현 코드</strong>다.</p>
<p>즉, 지금까지 만든 파일들은 제출용 결과물이 아니라 아래와 같은 역할을 한다.</p>
<ul>
<li>입력 파일을 정상적으로 읽는지 확인</li>
<li>계산 로직을 분리</li>
<li>edge 1건 기준 계산 결과를 검증</li>
<li>전체 edge 반복 계산이 잘 되는지 확인</li>
</ul>
<p>처음에는 “나는 최종 산출물 3개만 만들면 되는데 왜 자꾸 파일이 늘어나지?”라는 생각이 들었는데,<br />실제로는 이 중간 단계들이 있어야 마지막 결과물 생성 과정에서 어디가 잘못됐는지 빠르게 파악할 수 있다.</p>
<hr />
<h2 id="지금까지-만든-파일과-역할">지금까지 만든 파일과 역할</h2>
<h3 id="1-configpy">1. <code>config.py</code></h3>
<p>C단계에서 사용할 경로와 설정값을 관리하는 파일이다.<br />하드코딩을 줄이고, 나중에 실제 데이터 경로로 바꿀 때 수정 범위를 줄이기 위해 만들었다.</p>
<h3 id="2-load_inputspy">2. <code>load_inputs.py</code></h3>
<p>B단계 입력 데이터와 C단계 mock 데이터를 정상적으로 읽을 수 있는지 확인하는 입력 로더다.</p>
<p>이 단계에서 확인한 내용:</p>
<ul>
<li>edges 개수</li>
<li>nodes 개수</li>
<li>elevation map key 개수</li>
<li>summit 개수</li>
<li>duplicate edge id 여부</li>
</ul>
<p>즉, 본격적인 계산 전에 “입력 구조가 맞는가?”를 먼저 검증하는 역할이다.</p>
<h3 id="3-metricspy">3. <code>metrics.py</code></h3>
<p>C단계 계산 로직을 담당하는 순수 함수 파일이다.</p>
<p>분리한 기능은 다음과 같다.</p>
<ul>
<li><code>calculate_elevation_gain</code></li>
<li><code>calculate_slope_percent</code></li>
<li><code>classify_difficulty</code></li>
</ul>
<p>여기서 기준은 아래와 같이 고정했다.</p>
<ul>
<li><code>elevation_gain_m = elevation_end_m - elevation_start_m</code></li>
<li><code>slope_percent = (elevation_gain_m / distance_m) * 100</code></li>
<li><code>difficulty</code>는 <code>abs(slope_percent)</code> 기준<ul>
<li>0 이상 5 미만: <code>easy</code></li>
<li>5 이상 12 미만: <code>medium</code></li>
<li>12 이상: <code>hard</code></li>
</ul>
</li>
</ul>
<p>이렇게 계산 책임만 따로 분리해 두면, 이후 QA나 최종 저장 단계에서도 같은 기준을 재사용할 수 있다.</p>
<h3 id="4-build_edge_metricspy">4. <code>build_edge_metrics.py</code></h3>
<p>edge 1건과 <code>node_elevation_map</code>을 받아, 최종 산출물에 들어갈 계산 결과를 딕셔너리 형태로 만드는 함수다.</p>
<p>이 단계에서 생성되는 값은 다음과 같다.</p>
<ul>
<li><code>edge_id</code></li>
<li><code>start_node_id</code></li>
<li><code>end_node_id</code></li>
<li><code>distance_m</code></li>
<li><code>elevation_start_m</code></li>
<li><code>elevation_end_m</code></li>
<li><code>elevation_gain_m</code></li>
<li><code>slope_percent</code></li>
<li><code>difficulty</code></li>
</ul>
<p>즉, 이 파일은 나중에 <code>final_trail_dataset.geojson</code>의 각 feature properties를 만드는 기반이 된다.</p>
<h3 id="5-run_build_edge_metricspy">5. <code>run_build_edge_metrics.py</code></h3>
<p>전체 mock edge 데이터를 순회하면서 <code>build_edge_metrics()</code>가 정상적으로 적용되는지 확인하는 실행 파일이다.</p>
<p>이 단계에서는 실제 mock 데이터 3건에 대해 아래와 같은 계산 결과를 확인했다.</p>
<ul>
<li><code>E0001</code>: 경사도 <code>14.2</code> → <code>hard</code></li>
<li><code>E0002</code>: 경사도 <code>11.2</code> → <code>medium</code></li>
<li><code>E0003</code>: 경사도 <code>-18.5</code> → <code>hard</code></li>
</ul>
<p>특히 <code>E0003</code>처럼 내리막 구간도 고도차는 음수로 계산하고, 난이도는 절댓값 기준으로 판정되도록 의도한 설계가 잘 반영되는 것을 확인했다.</p>
<hr />
<h2 id="이번에-정리한-중요한-개념">이번에 정리한 중요한 개념</h2>
<p>이번 작업에서 가장 크게 정리된 부분은 아래 한 문장으로 요약할 수 있다.</p>
<p><strong>지금까지 만든 파일은 최종 산출물이 아니라, 최종 산출물 3개를 만들기 위한 내부 계산/검증용 코드다.</strong></p>
<p>이 구분이 중요했던 이유는, 처음부터 <code>final_trail_dataset.geojson</code> 하나를 바로 만드는 큰 파일로 가면 다음 문제가 생길 수 있기 때문이다.</p>
<ul>
<li>계산 로직 오류</li>
<li>QA 판정 오류</li>
<li>summit 연결 오류</li>
<li>저장 포맷 오류</li>
</ul>
<p>이런 문제들이 한 파일에 다 섞이면 디버깅이 어려워진다.<br />그래서 지금은 작은 단위로 나눠서 아래 순서대로 조립하고 있다.</p>
<ol>
<li>입력 확인</li>
<li>계산 로직 분리</li>
<li>edge 1건 계산</li>
<li>전체 edge 계산</li>
<li>QA 판정</li>
<li>summit 연결</li>
<li>최종 산출물 저장</li>
</ol>
<hr />
<h2 id="지금까지의-작업-흐름-요약">지금까지의 작업 흐름 요약</h2>
<p>현재까지는 다음 흐름까지 완료한 상태다.</p>
<ul>
<li>mock 데이터 파일 구성 완료</li>
<li><code>config.py</code> 생성 완료</li>
<li><code>load_inputs.py</code> 생성 및 입력 확인 완료</li>
<li><code>metrics.py</code> 생성 및 계산 함수 검증 완료</li>
<li><code>build_edge_metrics.py</code> 생성 및 edge 1건 계산 확인 완료</li>
<li><code>run_build_edge_metrics.py</code> 생성 및 전체 edge 계산 확인 완료</li>
</ul>
<p>즉, C단계 전체 파이프라인 중에서 <strong>입력 확인 + 계산 로직 검증 단계</strong>까지 마친 상태라고 볼 수 있다.</p>

<h2 id="다음-작업-방향">다음 작업 방향</h2>
<p>이제 다음 단계부터는 최종 산출물 3개에 직접 연결되는 흐름으로 가면 된다.</p>
<h3 id="1-final_trail_datasetgeojson">1. <code>final_trail_dataset.geojson</code></h3>
<ul>
<li>edge별 계산 결과 반영</li>

<ul>
<li>QA 실패 데이터 수집</li>

</ul>
<p>이제부터는 “내부 테스트 파일을 만드는 단계”에서 한 걸음 더 나아가,<br />실제로 최종 산출물 생성으로 연결되는 방향으로 구조를 조립해 나가면 된다.</p>

<h2 id="느낀-점">느낀 점</h2>
<p>이번 작업을 하면서 단순히 코드를 빨리 작성하는 것보다,<br />“이 파일이 최종 결과물인지, 아니면 최종 결과물을 만들기 위한 중간 도구인지”를 구분하는 것이 훨씬 중요하다는 걸 느꼈다.</p>
<p>특히 데이터 파이프라인 작업은 한 번에 크게 만들면 오히려 흐름을 놓치기 쉬웠고,<br />작은 단위로 끊어서 검증하면서 가는 방식이 훨씬 안정적이었다.</p>
<p>지금은 아직 최종 산출물 3개를 모두 만든 단계는 아니지만,<br />그 결과물을 만들기 위한 기반 로직을 하나씩 분리하고 검증했다는 점에서 의미 있는 진행이었다.</p>
