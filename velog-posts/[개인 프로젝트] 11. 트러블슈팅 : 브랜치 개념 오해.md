<h3 id="문제-상황">문제 상황</h3>
<p>DearSun 백엔드 작업 중 다음과 같은 문제가 발생했다.</p>
<ol>
<li><code>dev</code> 브랜치에 초기 <code>build.gradle</code> 세팅 업로드</li>
<li><code>feat/ai-reply</code> 브랜치에서 <code>build.gradle</code> 수정 및 AI 기능 구현</li>
<li><code>feat/ai-reply</code> 브랜치 commit &amp; push 완료</li>
<li>이후 <code>dev</code> 브랜치에 merge</li>
<li>로컬에서 <code>dev</code> pull</li>
</ol>
<p>그런데 <code>dev</code> 브랜치에는 <code>feat/ai-reply</code>에서 수정한 <code>build.gradle</code> 내용이 반영되지 않았다.</p>
<hr />
<h4 id="처음에-했던-착각">처음에 했던 착각</h4>
<p>나는 이렇게 생각했다.</p>
<blockquote>
<p>ai-reply 브랜치가 더 최신이니까<br />merge하면 dev도 자동으로 그 기준으로 최신화 되겠지?</p>
</blockquote>
<p>즉,<br />브랜치 = 최신 버전 덮어쓰기 개념으로 이해하고 있었다.</p>
<p>하지만 Git은 그런 구조가 아니다.</p>
<hr />
<h4 id="원인-분석">원인 분석</h4>
<p>Git의 merge는 덮어쓰기가 아니다.</p>
<h4 id="잘못-이해한-개념">잘못 이해한 개념</h4>
<pre><code>ai 브랜치가 최신
→ dev에 merge
→ ai 기준으로 전부 업데이트</code></pre><h4 id="실제-git-동작-방식">실제 Git 동작 방식</h4>
<p>Git은 두 브랜치의 변경 이력을 비교해서 합친다.</p>
<ul>
<li>같은 파일을 양쪽에서 수정했으면 → 충돌 발생</li>
<li>충돌 해결 시 어떤 내용을 남길지 선택</li>
<li>선택한 내용이 최종 결과가 됨</li>
</ul>
<p>즉,</p>
<p>merge는 최신 버전 기준 병합이 아니라<br />변경 이력 기반 병합이다.</p>
<hr />
<h3 id="실제-발생했을-가능성이-높은-상황">실제 발생했을 가능성이 높은 상황</h3>
<h4 id="시나리오-구조">시나리오 구조</h4>
<pre><code>dev:      A ---- B
               \
feat/ai:         C (build 수정)</code></pre><p>또는</p>
<pre><code>dev:      A ---- B ---- D (build 관련 변경)
               \
feat/ai:         C (build 수정)</code></pre><p>이 상태에서 merge 시:</p>
<ul>
<li>build.gradle 충돌 발생</li>
<li>dev 쪽 코드 선택</li>
<li>ai 수정 내용 사라짐</li>
<li>merge commit은 생성됨</li>
</ul>
<p>그래서</p>
<ul>
<li>merge는 되었지만</li>
<li>build 수정 내용은 반영되지 않은 상태</li>
</ul>
<p>가 발생한 것이다.</p>
<hr />
<h3 id="확인-방법">확인 방법</h3>
<pre><code class="language-bash">git log dev -- build.gradle
git log feat/ai-reply -- build.gradle
git diff dev feat/ai-reply -- build.gradle</code></pre>
<p>이 명령어로</p>
<ul>
<li>각 브랜치에서 build 파일이 어떻게 변경되었는지</li>
<li>실제 차이점이 무엇인지</li>
</ul>
<p>확인할 수 있다.</p>
<hr />
<h3 id="핵심-깨달음">핵심 깨달음</h3>
<p>브랜치는 버전 덮어쓰기가 아니다.</p>
<p>브랜치는 단순한 복사본이 아니라<br />히스토리 그래프 위의 분기점이다.</p>
<p>merge는</p>
<p>현재 브랜치에<br />다른 브랜치의 변경 이력을 합치는 작업이다.</p>
<hr />
<h3 id="배운-점">배운 점</h3>
<ul>
<li>merge는 최신 기준 자동 업데이트가 아니다.</li>
<li>충돌 해결 시 어떤 코드를 선택했는지가 최종 결과를 결정한다.</li>
<li>merge 됐다와 내 코드가 반영됐다는 다른 의미다.</li>
<li>merge 후 반드시 diff로 확인해야 한다.</li>
</ul>
<hr />
<h3 id="앞으로의-개선-방법">앞으로의 개선 방법</h3>
<ol>
<li>PR 후 merge 완료 여부 반드시 확인</li>
<li>merge 후 git diff로 실제 반영 여부 확인</li>
<li>중요한 설정 파일(build.gradle 등)은 충돌 시 꼼꼼히 비교</li>
<li>merge 전에 항상 최신 dev를 pull 받고 작업 시작</li>
</ol>
<hr />
<h3 id="정리">정리</h3>
<p>이번 이슈의 본질은 코드 문제가 아니라<br />Git 브랜치 개념에 대한 오해였다.</p>
<p>최신 브랜치가 기준이 되는 것이 아니라<br />변경 이력이 합쳐진다는 개념으로 이해해야 한다.</p>
<p>이번 경험을 통해 DearSun 프로젝트에서 Git 흐름을 더 정확히 이해하게 되었다.</p>
