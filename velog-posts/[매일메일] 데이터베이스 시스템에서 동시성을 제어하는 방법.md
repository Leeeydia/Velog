<p>대표적인 동시성 제어 방식으로 <code>MVCC</code>(Multi-Version Concurrency Control) 와 <code>Lock-Based Concurrency Control</code>이 있습니다.</p>
<blockquote>
<p>MVCC</p>
</blockquote>
<p>MVCC는 데이터의 여러 버전을 유지하여 트랜잭션이 동시에 데이트를 읽고 쓸 수 있도록 하는 방식입니다.
각 트랜잭션은 자신만의 <strong>일괄된 스냅샷</strong>을 기반으로 데이터를 읽어, 
다른 트랜잭션의 변경사항에 영향을 받지 않습니다.</p>
<ul>
<li><p>데이터의 각 버전을 유지하여 읽기 / 쓰기 작업이 독립적으로 이루어 질 수 있습니다.</p>
</li>
<li><p>읽기 작겁시 잠금을 사용하지 않아 높은 동시성을 제공합니다.</p>
</li>
<li><p>읽기 작업시 잠금을 사용하지 않으므로, 쓰기 작업과의 충돌이 줄어듭니다. 하지만 여러 버전의 데이터를 유지해야 하므로 저장 공간이 더 많이 필요합니다</p>
</li>
<li><p>트랜잭션이 시작된 시점의 데이터 상태를 기반으로 읽기 작업을 수행하여 일관성을 유지합니다</p>
</li>
</ul>
<blockquote>
<p>Lock-Based Concurrency Control</p>
</blockquote>
<ul>
<li>잠금(Lock) 을 사용하여 동시성을 제어합니다.</li>
<li><blockquote>
<p>데이터를 읽거나 수정할 때 해당 데이터에 잠금을 걸어 다른 트랜잭션의 접근을 제한하기 때문에
데이터의 일관성과 무결성을 직접적으로 제어할 수 있습니다.</p>
</blockquote>
</li>
</ul>
<p>-&gt; 읽기 작업은 공유 잠금, 쓰기 작업은 배타 잠금을 사용하여 동시성을 제어합니다</p>
<p>-많은 다수의 트랜잭션이 동일한 데이터에 접근하는 경우 성능 저하가 발생할 수 있습니다</p>
<ul>
<li>잘못된 잠금 순서나 설계로 인해 교착상대 (Deadlock)가 발생할 위험이 있습니다.</li>
</ul>
<blockquote>
<p>정리 !
MySQL의 InnoDB는 MVCC와 Lock-Based Concurrency Control을 함께 사용합니다.</p>
</blockquote>
<p>일반적인 읽기 트랜잭션은 MVCC를 사용하여 스냅샷 기반으로 데이터를 읽기 때문에 잠금을 사용하지 않고, 높은 동시성을 유지할 수 있습니다.</p>
<p>반면, 데이터를 변경하는 쓰기 트랜잭션은 잠금을 사용하여 동시에 같은 데이터를 수정하는 것을 방지하고, 데이터의 일관성과 무결성을 보장합니다.</p>
<h3 id="🔍-배운-점">🔍 배운 점</h3>
<p>백엔드를 처음 배우면서 가장 크게 느낀 점은,
코드는 혼자 동작하지 않고 항상 흐름 속에서 움직인다는 것이었다.</p>
<p>처음에는</p>
<p>SQL = DB라고 생각했고</p>
<p>SELECT, INSERT 같은 명령어도
“외워야 하는 문법” 정도로만 받아들였다.</p>
<p>그래서</p>
<p><strong>요청 → 로직 → DB → 결과 반환</strong></p>
<p>이라는 구조가 눈에 보이지 않아 많이 막막했다.</p>
<p>하지만 JDBC로 직접 SQL을 실행하고,
매일메일을 통해 트랜잭션 개념과 동시성 제어(MVCC, Lock)를 배우면서
<strong>“아, DB는 그냥 저장소가 아니라 여러 요청을 동시에 처리하는 시스템이구나”</strong>라는 걸 이해하게 되었다.</p>
<p>특히 InnoDB가</p>
<p>읽기에서는 MVCC를 사용해 잠금 없이 데이터를 조회하고</p>
<p>쓰기에서는 Lock을 통해 데이터 충돌을 막는다는 점을 보며</p>
<p>왜 어떤 쿼리는 빠르고, 어떤 상황에서는 기다림이 발생하는지
그 이유를 구조적으로 설명할 수 있게 된 것이 큰 변화였다.</p>
<p>이제는 SQL을
“그냥 실행되는 명령어”가 아니라
트랜잭션 안에서 데이터의 일관성과 안전성을 지키기 위한 도구로 바라보게 되는 계기가 되었다.</p>
